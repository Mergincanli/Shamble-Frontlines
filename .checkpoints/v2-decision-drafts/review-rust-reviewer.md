## What I checked and found sound (so nobody re-checks it)
- ADR 0004 part 7's float rules (libm pinned, parry3d's `enhanced-determinism`, baseline x86-64, `simd128` off until
  measured, NaN banned at entry) and their marks PM-0004-19 to -26: right, and the suite runs on seven targets.
- ADR 0002 part 4's overflow rule (checks on for `sim` and `protocol` in every profile, explicit wrapping counters) with
  its cost reported (PM-0002-53): right.
- ADR 0001's decoder rules ("returns an error and never panics, and checks sizes before it allocates; the sim thread
  never parses raw network bytes", 0001:321–322), the hostile-input limits (0001:327–333), the bounded per-client
  queues, and PM-0001-34's 10 million fuzzed inputs per message type: sound for 48 players. One room per process, with
  connection work isolated, is the right containment; finding 3 only closes its tick-thread hole.
- ADR 0005 CD-1 and CD-2: `float_roundtrip`, integers within a double's exact range, a byte cap before parsing,
  serde_json's depth limit, a maximum length on every collection, and a fuzzed no-panic loader. This bounds every
  allocation a payload can cause. serde_json's maps are `BTreeMap` or insertion-ordered, so the untyped-tree migration
  is deterministic either way.
- PM-0002-3's "at most 4 Wasm calls per tick, glue included" is reachable. It needs the control API to return plain
  integers (offsets) and to take inbound bytes through a Rust-owned buffer whose address the host learns once. A naive
  `&[u8]` parameter adds `__wbindgen_malloc` per call, and a by-value struct return adds the stack-pointer calls. The
  counting build will show which (no draft change needed; a note for the spike).
- std `HashMap` is "not randomized" on `wasm32-unknown-unknown` (the rustc book's page for the target, read
  2026-11-02), so a leaking map order shows between the two native processes with different seeds. PM-0004-18 already
  forces exactly that.

## Questions for Mustafa or the Advisor
- **Q1 (POOL-FULL), for Mustafa through game-designer.** When too many projectiles or effects are alive at once (a pool
  is full), which gives way? Why it matters: the sim must have a fixed limit to run without stalls, and the rule
  decides who wins in a pile-up (finding 4). Options: (a) the new one is refused (it never changes what already
  exists); (b) the oldest one ends early. Recommendation: (a), with a counter so tuning sees it if it ever happens;
  game-designer may pick (b) for kinds where refusing feels wrong. Decider: game-designer proposes per kind; Mustafa
  confirms where a player could notice.
- **Q2 (ROOM-CRASH), for the Advisor.** When the server's simulation crashes mid-match, does the match end, or does
  the room try to continue? Why it matters: it decides finding 3's fix. Options: (a) the match ends: clients get
  "match ended", the crash is reported, and the process exits; (b) the room restores its last snapshot and continues.
  Recommendation: (a). No VISION_V2 §6 item asks for resuming, and a half-run tick leaves state that cannot be trusted.
  (b) would be a generic feature added for later.
