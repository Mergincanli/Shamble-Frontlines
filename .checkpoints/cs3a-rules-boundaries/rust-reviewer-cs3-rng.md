1. Seed: 32 bytes, drawn by the host (server: OS secure source; local play: the Worker's crypto.getRandomValues) and passed in; the sim reads no random source itself (so no getrandom / os_rng feature in the tree). Today World holds `seed: [u8; 32]` (world.rs:10,18), in the 36 canonical bytes and the FNV-1a state hash (world.rs:49-65).
2. Several named streams per match, one per purpose: match setup, weapon spread, bot decisions, ability procs, upgrade offers; all authority-only today (:320-327). So: one seed, many independent streams (ChaCha's 64-bit stream id, or per-purpose seeds).
3. A position that can be saved and restored: the streams' state (seed, stream, position) is authority state and in the state hash (:319-320; part 9 :343-344 "the streams' state" in the canonical bytes); S8: "a stream saved mid-match and restored continues identically". Needs get/set of word position at a fixed width (no usize).
4. Identical output native and wasm32: "the first 10,000 outputs of each stream, and of the sim's own sampling functions on them, equal pinned test vectors on every target of PM-0004-19" (PM-0004-27). 6. The generator ships in every client's Wasm (the sim crate does), so size counts and seeds/state of authority-only streams must stay out of the client's predicting state (PM-0004-29).

BLOCK 5 (the test vectors), written:
- Where they come from: a small generator script committed beside the vectors (Python or Node, written from the ChaCha description, not from either crate), which first checks itself against the 8 published 8-round/256-bit vectors of the Strombergson draft (and the 12- and 20-round ones, free), then writes the stream files. - What to pin per stream (PM-0004-27, S8): a fixed public test seed (e.g. the draft's TC8 key; never a real match seed), each of the sim's stream ids (match setup, weapon spread, bot decisions, ability procs, offers); 10,000 next_u32 words from word 0; 10,000 next_u64 values starting at word 1 (pairs straddle the 16- and 64-word block edges); one save-and-restore at a mid-block word (seed, stream, word position written to canonical bytes, read back, the next 1,000 words equal); one window across the 2^32-block carry (96 words from block 2^32 - 1, as rand's test does). The sampling functions' vectors join when those functions exist.
- Format and size: raw little-endian binary, 40,000 B per stream for the u32 view (80,000 B for the u64 view); 5 streams x 120,000 B = about 600 KB, or about 200 KB with the u32 view only; a text manifest beside it: seed hex, stream ids, counts, start positions, SHA-256 of each section, and the script's name. Hex text would double the size and be diff noise. `include_bytes!` in Rust, `readFileSync` in Node read the same file.
- Native: `cargo test -p sim --locked` and again with `--release` (overflow checks on in release). If (b): also once with RUSTFLAGS `--cfg chacha20_backend="soft"` and once with `"sse2"`, because CI's x86 machine runs the AVX2 path at run time (rng.rs:70-80) and the server could run any of the three. If (a): native runs the SSE2 SIMD path (ppv-lite86 without std, compile time). If (c): one code path, nothing to force.
- WebAssembly: the route that fits today's set-up is the boundary test: one exported call in sim-wasm (seed, stream id, start word, count -> the words, written into linear memory like the block, or returned as a Uint32Array) and a test in packages/sim-worker/boundary/sim-wasm.test.mjs that loads the built sim_wasm_bg.wasm (node packages/client/scripts/build.mjs --wasm-only) and compares every word with the same file, reporting the first differing index.
