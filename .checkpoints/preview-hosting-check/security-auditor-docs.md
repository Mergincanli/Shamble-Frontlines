## G4 Which ref a deployment-branch rule checks for a pull_request job; the refusal error (DONE)
Short answer: the rule is matched against GITHUB_REF, which for `pull_request` (opened/synchronize/reopened, and closed-without-merge) is `refs/pull/<N>/merge`, so neither the head nor the base branch name: a `main`-only rule refuses it unless a rule `refs/pull/*/merge` is added. BUT for `closed` after a merge, GITHUB_REF is the base branch's ref (e.g. refs/heads/main), so a closed-merged run passes a `main`-only rule (see G5; finding below). Error: the official docs page does not quote the message; GitHub's 2021 changelog says the job fails and the run stops; the message seen in public run logs is `Branch "<ref>" is not allowed to deploy to <env> due to environment protection rules.` (not an official doc).
- https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments (read 2026-11-15): "The deployment branch or tag rule is matched against the `GITHUB_REF` of the workflow run. For values of `GITHUB_REF` for each workflow trigger, see Events that trigger workflows. If you specify `releases/*` as a deployment branch or tag rule, only a `GITHUB_REF` whose name begins with `releases/` can deploy to the environment. Adding another branch rule for `refs/pull/*/merge` would also allow workflows triggered by `pull_request` events to deploy to the environment. Wildcard characters will not match `/`..." / Note on "Protected branches only": "Deployment workflow runs triggered by tags with the same name as a protected branch and forks with branches that match the protected branch name cannot deploy to the environment."
- https://github.blog/changelog/2021-02-17-github-actions-limit-which-branches-can-deploy-to-an-environment/ (dated 2021-02-17; read 2026-11-15 via a summariser, fragments): "When a job tries to deploy to an environment with Deployment branches configured" ... "Actions will check the value of `github.ref` against the configuration" ... "if it does not match the job will fail and the run will stop."
- Error text: not found on docs.github.com (looked: deployments-and-environments, manage-environments, control-deployments, review-deployments). Seen in third-party run logs and a community discussion (github.com/orgs/community/discussions/39054): `Branch "x" is not allowed to deploy to github-pages due to environment protection rules.` Treat as unofficial.
- (finding, for PM-0002-66) The changelog says the job "will fail"; no page says whether any step runs. Inference: a branch-refused job runs no steps, so its "absent even when approved" print may never appear (and no review is asked). The spike should record what is actually shown (job conclusion, annotation text, whether any step log exists) instead of expecting a printed "absent".
- (finding, Medium, for B9 / PM-0006-32) A `pull_request` workflow with `types: [closed]` that runs after a MERGE gets GITHUB_REF = the base ref (refs/heads/main), so a job in it naming `production` passes a `main`-only rule. The code that runs is the merge commit on main (already merged, so behind main's review), so this is not a bypass for an unmerged branch, but the production refusal test must use an open PR (opened/synchronize) or a closed-unmerged one; and production deploys should be keyed to `push` on main only (ADR 0002 part 10 already says so).
Confidence: high on GITHUB_REF matching (quoted); error text medium (unofficial).

## G5 The pull_request event: which workflow file, GITHUB_SHA, GITHUB_REF; deleted workflow; same-repo vs fork (DONE)
Short answer: one row for all activity types: GITHUB_SHA "Last merge commit on the GITHUB_REF branch", GITHUB_REF "PR merge branch refs/pull/N/merge"; except closed: unmerged keeps refs/pull/N/merge, merged gives the base branch's fully qualified ref. The workflow file used is "the version ... present in the associated commit SHA or Git ref of the event", i.e. the merge commit (so the PR's own edits). Default types: opened, synchronize, reopened; `closed` needs `types:`. Deleted workflow at close: not stated; inference: if the file is absent from the PR's merge commit (closed unmerged) it does not run, so a PR can switch off its own close-cleanup workflow. For a merged PR the file is read from the merge result on the base (inference from the same rule). Same-repo PR: secrets not withheld (only fork runs are stated to lose them) and GITHUB_TOKEN gets the repository default adjusted by the workflow's `permissions`; fork PR: no secrets except GITHUB_TOKEN, and GITHUB_TOKEN write permissions forced to read (unless "Send write tokens to workflows from pull requests", a private-repo fork setting); first-time contributors may need approval.
- https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request (read 2026-11-15):
  - Table: activity types incl. opened, closed, reopened, synchronize | GITHUB_SHA: "Last merge commit on the `GITHUB_REF` branch" | GITHUB_REF: "PR merge branch `refs/pull/PULL_REQUEST_NUMBER/merge`".
  - "By default, a workflow only runs when a `pull_request` event's activity type is `opened`, `synchronize`, or `reopened`. To trigger workflows by different activity types, use the `types` keyword."
  - "The value of `GITHUB_REF` varies for a closed pull request depending on whether the pull request has been merged or not. If a pull request was closed but not merged, it will be `refs/pull/PULL_REQUEST_NUMBER/merge`. If a pull request was closed as a result of being merged, it will be the fully qualified `ref` of the branch it was merged into, for example `/refs/heads/main`."
  - "Note that `GITHUB_SHA` for this event is the last merge commit of the pull request merge branch. If you want to get the commit ID for the last commit to the head branch of the pull request, use `github.event.pull_request.head.sha` instead."
  - "Workflows will not run on `pull_request` activity if the pull request has a merge conflict." (inference: a branch can also suppress its own close workflow by creating a conflict).
  - "With the exception of `GITHUB_TOKEN`, secrets are not passed to the runner when a workflow is triggered from a forked repository. The `GITHUB_TOKEN` has read-only permissions in pull requests from forked repositories."
  - "When a first-time contributor submits a pull request to a public repository, a maintainer with write access may need to approve running workflows on the pull request."
  - pull_request_target: "This event runs in the context of the default branch of the base repository, rather than in the context of the merge commit, as the `pull_request` event does."
  - "When a pull request is created or updated by a workflow using `GITHUB_TOKEN`, `pull_request` events with the `opened`, `synchronize`, or `reopened` activity types create workflow runs that require approval."
  - `schedule`: "This event will only trigger a workflow run if the workflow file exists on the default branch." (so a weekly sweep is main-controlled).
- https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows (read 2026-11-15): "GitHub searches the `.github/workflows` directory in the root of your repository for workflow files that are present in the associated commit SHA or Git ref of the event." / "Each workflow run will use the version of the workflow that is present in the associated commit SHA or Git ref of the event."
- https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax (permissions section, read 2026-11-15): "The permissions for the `GITHUB_TOKEN` are initially set to the default setting for the enterprise, organization, or repository. ... The permissions are then adjusted based on any configuration within the workflow file, first at the workflow level and then at the job level. Finally, if the workflow was triggered by a pull request event other than `pull_request_target` from a forked repository, and the Send write tokens to workflows from pull requests setting is not selected, the permissions are adjusted to change any write permissions to read only."
- https://docs.github.com/en/actions/reference/workflows-and-actions/contexts (read 2026-11-15): `github.actor`: "The username of the user that triggered the initial workflow run." `github.triggering_actor`: "The username of the user that initiated the workflow run. ... Any workflow re-runs will use the privileges of `github.actor`".

The weekly `schedule` sweep runs from main and is the only cleanup a branch cannot switch off (inference). PM-0006-6's bite (d) covers "close workflow switched off" but not "edited by the PR itself".
- Not found: an explicit sentence that same-repository PR runs receive repository/environment secrets (only the fork exclusion is stated). Inference from that exclusion and from secure-use ("Any user with write access to your repository has read access to all secrets configured in your repository").
Confidence: high on the table and the closed-ref note (quoted); deleted-file behaviour inference medium-high.
