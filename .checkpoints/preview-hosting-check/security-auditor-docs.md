## G4 Which ref a deployment-branch rule checks for a pull_request job; the refusal error (DONE)
Short answer (refusal-before-steps: see the PM-0002-66 finding, an inference): the rule is matched against GITHUB_REF, which for `pull_request` (opened/synchronize/reopened, and closed-without-merge) is `refs/pull/<N>/merge`, so neither the head nor the base branch name: a `main`-only rule refuses it unless a rule `refs/pull/*/merge` is added. BUT for `closed` after a merge, GITHUB_REF is the base branch's ref (e.g. refs/heads/main), so a closed-merged run passes a `main`-only rule (see G5; finding below). Error: the official docs page does not quote the message; GitHub's 2021 changelog says the job fails and the run stops; the message seen in public run logs is `Branch "<ref>" is not allowed to deploy to <env> due to environment protection rules.` (not an official doc).

## G5 The pull_request event: which workflow file, GITHUB_SHA, GITHUB_REF; deleted workflow; same-repo vs fork (DONE)
Short answer: one row for all activity types: GITHUB_SHA "Last merge commit on the GITHUB_REF branch", GITHUB_REF "PR merge branch refs/pull/N/merge"; except closed: unmerged keeps refs/pull/N/merge, merged gives the base branch's fully qualified ref. The workflow file used is "the version ... present in the associated commit SHA or Git ref of the event", i.e. the merge commit (so the PR's own edits). Default types: opened, synchronize, reopened; `closed` needs `types:`. Deleted workflow at close: not stated; inference: if the file is absent from the PR's merge commit (closed unmerged) it does not run, so a PR can switch off its own close-cleanup workflow. For a merged PR the file is read from the merge result on the base (inference from the same rule). Same-repo PR: secrets not withheld (only fork runs are stated to lose them) and GITHUB_TOKEN gets the repository default adjusted by the workflow's `permissions`; fork PR: no secrets except GITHUB_TOKEN, and GITHUB_TOKEN write permissions forced to read (unless "Send write tokens to workflows from pull requests", a private-repo fork setting); first-time contributors may need approval.
- https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request (read 2026-11-15):
  - Table: activity types incl. opened, closed, reopened, synchronize | GITHUB_SHA: "Last merge commit on the `GITHUB_REF` branch" | GITHUB_REF: "PR merge branch `refs/pull/PULL_REQUEST_NUMBER/merge`".
  - "By default, a workflow only runs when a `pull_request` event's activity type is `opened`, `synchronize`, or `reopened`. To trigger workflows by different activity types, use the `types` keyword."
  - "The value of `GITHUB_REF` varies for a closed pull request depending on whether the pull request has been merged or not. If a pull request was closed but not merged, it will be `refs/pull/PULL_REQUEST_NUMBER/merge`. If a pull request was closed as a result of being merged, it will be the fully qualified `ref` of the branch it was merged into, for example `/refs/heads/main`."
  - "Note that `GITHUB_SHA` for this event is the last merge commit of the pull request merge branch. If you want to get the commit ID for the last commit to the head branch of the pull request, use `github.event.pull_request.head.sha` instead."
  - "The `pull_request` webhook event payload is empty for merged pull requests and pull requests that come from forked repositories." (bears on how a close job learns the head branch for PM-0006-6 case (b); proposed spike observation: log which `github.event.pull_request` fields, e.g. head.ref, the closed-merged run actually sees; `github.head_ref` may be the fallback, not verified)
  - "Workflows will not run on `pull_request` activity if the pull request has a merge conflict." (inference: a branch can also suppress its own close workflow by creating a conflict).
  - "With the exception of `GITHUB_TOKEN`, secrets are not passed to the runner when a workflow is triggered from a forked repository. The `GITHUB_TOKEN` has read-only permissions in pull requests from forked repositories."
  - "When a first-time contributor submits a pull request to a public repository, a maintainer with write access may need to approve running workflows on the pull request."
  - pull_request_target: "This event runs in the context of the default branch of the base repository, rather than in the context of the merge commit, as the `pull_request` event does."
  - "When a pull request is created or updated by a workflow using `GITHUB_TOKEN`, `pull_request` events with the `opened`, `synchronize`, or `reopened` activity types create workflow runs that require approval."
  - `schedule`: "This event will only trigger a workflow run if the workflow file exists on the default branch." (so a weekly sweep is main-controlled).
- https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows (read 2026-11-15): "GitHub searches the `.github/workflows` directory in the root of your repository for workflow files that are present in the associated commit SHA or Git ref of the event." / "Each workflow run will use the version of the workflow that is present in the associated commit SHA or Git ref of the event."

## G10 Threat model of the preview hosting check (DONE; every line not quoted above is an INFERENCE)
Assets: the Pages token(s) in `preview` and `production`; the Cloudflare account's projects (the check's project, and anything else in that account); the production URL; Mustafa's approval.
Actors: (A) an agent session pushing a branch of TR as Mustafa's login; (B) a fork contributor (anyone; TR is public); (C) whoever obtains a token value.
1. Same-repository pull request (A). Reaches: its own workflow file (runs from the PR merge commit, G5), the repo-default GITHUB_TOKEN raised by its own `permissions:` key (G8 quote), and every non-environment repository secret (G5/G1b; TR should hold none). It reaches an environment secret only after the environment's rules pass (G1). `production` with Selected branches = `main`: refused while the PR is open or closed-unmerged (GITHUB_REF refs/pull/N/merge, G4); a closed-merged run gets refs/heads/main and passes (G4, G5) but its code is already on main. `preview` with a required reviewer: waits for a reviewer, BUT the reviewer is Mustafa's login, the same login the session runs as: with Prevent self-review OFF, a session holding his credential with repo scope (classic) or Deployments write (fine-grained) can approve via POST .../pending_deployments (G3); with it ON, Mustafa cannot approve session-started runs either and only the admin bypass is left, which the same login also holds (G1, G3).
