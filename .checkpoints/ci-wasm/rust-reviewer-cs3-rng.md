1. Seed: 32 bytes, drawn by the host (server: OS secure source; local play: the Worker's crypto.getRandomValues) and passed in; the sim reads no random source itself (so no getrandom / os_rng feature in the tree). Today World holds `seed: [u8; 32]` (world.rs:10,18), in the 36 canonical bytes and the FNV-1a state hash (world.rs:49-65).
2. Several named streams per match, one per purpose: match setup, weapon spread, bot decisions, ability procs, upgrade offers; all authority-only today (:320-327). So: one seed, many independent streams (ChaCha's 64-bit stream id, or per-purpose seeds).
3. A position that can be saved and restored: the streams' state (seed, stream, position) is authority state and in the state hash (:319-320; part 9 :343-344 "the streams' state" in the canonical bytes); S8: "a stream saved mid-match and restored continues identically". Needs get/set of word position at a fixed width (no usize).
4. Identical output native and wasm32: "the first 10,000 outputs of each stream, and of the sim's own sampling functions on them, equal pinned test vectors on every target of PM-0004-19" (PM-0004-27). A backend (SIMD/soft) choice that could change output must never exist; neither a seed from the clock (the mark's "Bites").
5. Raw output only, mapped by the sim's own sampling functions; never rand's distributions (R1-DET-OQ5: no value-stability statement; uniform floats "may equal high"). So only the core trait (next_u32/next_u64/fill_bytes) is needed, not the rand crate.
6. The generator ships in every client's Wasm (the sim crate does), so size counts and seeds/state of authority-only streams must stay out of the client's predicting state (PM-0004-29).
7. no_std: the draft does not ask for it (sim is std today: Vec in world.rs); but a no_std-capable, default-features-off crate keeps std/getrandom out.
8. Cost: ChaCha8's cost per tick (mean, p99) at N = 48 reported (PM-0004-27), deciding whether R1-DET-OQ11 (a PCG fallback) returns.
9. Repo rules that bite a new crate: root Cargo.toml turns overflow-checks ON for each third-party crate by name (OVERFLOW-ALL), so the crate must use wrapping ops explicitly (check its source); `unsafe_code = "deny"` binds our crates only; Rust pinned 1.99.1 (rust-toolchain.toml), edition 2024; Cargo.lock today: no rand_core/chacha/ppv-lite86/zerocopy/cpufeatures; cfg-if 1.0.5 is already in.

BLOCK 2 CONCLUSION: the guide says the chacha20 types "are a direct replacement for the like-named `rand_chacha` types; these maintain reproducibility of output and have a similar API" (section PRNGs). It is silent on seed, stream, word position, word order and fill_bytes vs next_u32/next_u64. By the source: same state layout, same 4-block buffer, same rand_core 0.10 BlockRng code for next_u32/next_u64/fill_bytes, so the same 32-byte seed gives the same 10,000 outputs from both crates' ChaCha8Rng, provided set_stream is called before any draw and before set_word_pos. No source says the outputs differ; no test in either project proves the 8-round equality.
