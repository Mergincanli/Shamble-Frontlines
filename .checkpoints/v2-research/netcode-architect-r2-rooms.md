S1. https://docs.aws.amazon.com/gameliftservers/latest/developerguide/gamelift-sdk-interactions.html "Game client/server interactions with Amazon GameLift Servers" (official AWS; no page date shown; server SDK version not named on page), read 2026-10-27. Says: process starts -> InitSDK -> ProcessReady (reports connection info) -> service marks process ACTIVE; onHealthCheck periodically, must answer within one minute, else stops getting sessions. Game session: backend -> StartGameSessionPlacement (ticket PENDING) -> service finds "an active server process that's not hosting a game session" -> GameSession ACTIVATING -> onStartGameSession -> "Changes the server process's number of game sessions to 1" -> server calls ActivateGameSession when ready to accept players -> ACTIVE, ticket FULFILLED -> backend passes connection info, client connects directly to IP:port. Player: backend CreatePlayerSession (session must be ACTIVE, open slot) -> RESERVED -> client connects with player session id -> server calls AcceptPlayerSession to validate -> ACTIVE; if not accepted "within a certain time period" -> TIMEDOUT and slot reopens. Disconnect -> server RemovePlayerSession -> COMPLETED, slot reopens. End: ProcessEnding, Destroy, logs uploaded, session + process TERMINATED, new process may start. Sure: confirmed. Implies one session per process at a time (inferred from "not hosting a game session" + "number of game sessions to 1").

S5. https://learn.microsoft.com/en-us/gaming/playfab/multiplayer/servers/multiplayer-game-server-lifecycle "Lifecycle of a multiplayer server - PlayFab" (official Microsoft; ms.date 2022-01-26, updated_at 2025-05-01), read 2026-10-27. S11. https://gafferongames.com/post/why_cant_i_send_udp_packets_from_a_browser/ "Why can't I send UDP packets from a browser?" (Glenn Fiedler, Gaffer On Games, 2017-02-26; tier: talks/articles from shipped-game engineers), read 2026-10-27. Web backend authenticates (e.g. OAuth), client makes REST call over HTTPS, gets a base64 "connect token"; private portion "encrypted and signed by the shared private key using an AEAD primitive from libsodium"; public portion has what the client needs to connect; tokens "rely on a shared private key between the web backend and the dedicated server instances"; "Connect tokens are short lived"; expiry covered by signature; token lists the dedicated server addresses it is valid for; server rejects reuse by "searching a short history of connect token HMACs" ("prevents one connect token from being used to connect multiple clients"); "only one client by unique client id may be connected at any time"; connection times out after ~5 s of silence. Reconnect not discussed. Sure: confirmed.
S12. https://raw.githubusercontent.com/mas-bandwidth/netcode/main/STANDARD.md "netcode 1.02" standard (Glenn Fiedler's netcode protocol, main branch; tier: shipped-game engineer spec/other), read 2026-10-27. Connect token fields: version "NETCODE 1.02", protocol id (64-bit per game), create and expire timestamps, 24-byte random nonce, timeout seconds, 1-32 server addresses, client id ("globally unique identifier for an authenticated client"), 256 bytes user data; private part libsodium AEAD with key shared between web backend and dedicated servers. Server checks in order: expired -> ignore; own address not in list -> ignore; client id already connected -> ignore; token history keyed by HMAC ("A connect token is therefore usable for exactly one connection"); adds an encryption mapping per source address. After a server restart a rejected client should "request a new connect token from the web backend". Sure: confirmed.
