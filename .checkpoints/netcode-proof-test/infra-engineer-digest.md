- Host key check (for security-auditor; Rec): cloud-init's default prints the host key fingerprints to the VM's console at first boot (standard behaviour, not read today); Mustafa reads them in the Hetzner console's screen (R6), or the PC session compares the first connection's fingerprint with a file the VM serves over its browser-trusted `wss` port (the trust then rests on the Let's Encrypt certificate for that name). `StrictHostKeyChecking=accept-new` without a check is not enough (SP:65-66 asks for a check).

## G. DNS and certificates
**Records (Rec; Cloudflare dashboard fields, CF1-CF3).** In the Cloudflare "Name" field a name is written relative to the zone.
| host | Type | Name | Content (value) | TTL | Proxy status | needed when |
|---|---|---|---|---|---|---|
| RS (`wss` leg, the hash endpoint, and the WebTransport URL) | A | `rs.nt` (= rs.nt.shamblefrontlines.com) | `<RS's IPv4 of the day>` | 1 min (60 s, the non-Enterprise floor, CF2) | DNS only (grey cloud) | every run whose browsers use `wss`, or fetch the hash from RS; set before the certificate is issued (0006:1278-1279) |
| spare RS name | A | `rs-b.nt` | `<RS's IPv4 of the day>` | 1 min | DNS only | only if `rs.nt` would get a 6th certificate within 7 days (LE2, below) |
| LG | A | `lg.nt` | `<LG's IPv4 of the day>` | 1 min | DNS only | only if the route needs it: route (1)'s results server, or RS finding LG by name; not needed in route (3) |
Why "DNS only" works: Cloudflare then "responds with your server's actual IP address and does not route HTTP/HTTPS traffic through its network" (CF1); a proxied record would carry only HTTP(S) and never the UDP of WebTransport. It also "exposes your origin IP address to anyone who queries the record" (CF1): harmless for a VM that lives a few hours, and the firewall still applies. Why 60 s: a new address each run day (0006:1274-1276), and "updates to your records take longer" with a longer TTL (CF2). Rec: delete or blank the record when the VMs are deleted, so the name never points at an address Hetzner hands to someone else.
**AAAA:** Rec none for the proof test. With an AAAA record, browsers may pick IPv6, which changes header sizes beside PM-0001-14's datagram cap and PM-0006-17's "48 bot clients over IPv4" case (0006:1355), and Let's Encrypt would validate over IPv6 too. The VMs still keep their IPv6 address (part 5, 0006:225); an IPv6 leg can be a separate, recorded case later.
**CAA (optional, Rec low priority):** Type CAA, Name `@`, Tag "issue" (only allow specific hostnames), CA domain name `letsencrypt.org`. Gain: no other public CA may issue for the domain. Cost: "If you have CAA records on your domain, they must permit the certificate authority (CA) that Cloudflare uses"; Cloudflare adds its own CAA records automatically with Universal SSL once any CAA record exists (CF3), so the future client host on this domain keeps working; a later CA change needs an edit. No `accounturi` binding: each run makes a new ACME account.

Rate limits (LE2, lastmod 2026-08-05): 50 certificates per registered domain per 7 days; **5 per exact same set of names per 7 days** (refills 1 per 34 hours); 5 failed authorizations per name per account per hour; 300 new orders per account per 3 h. Rec: issue only in sessions with a browser `wss` leg, keep a ledger of issuances in the results log, switch to `rs-b.nt` before a 6th, and do the first dry run against Let's Encrypt's staging service (not browser-trusted; its limits are separate from production's: not read today). Lifetime 90 days by default, 6 days opt-in (LE3); the 6-day profile suits a VM that lives hours. Every issued name lands in public Certificate Transparency logs and "automated CT crawling bots will be able to discover your domain, attempt to access it" (LE3): expect stray probes on the game ports; the firewall and join tokens contain them; the results should record that stray traffic exists.

**The WebTransport development certificate** (ECDSA P-256, valid at most 14 days, made by the server at start, pinned through `serverCertificateHashes`: 0006:302-305; PM-0006-25, 0006:1363):
- Made where: on RS by the room server or its supervisor at start, one per VM, never in the repository; PM-0006-27's 15-day certificate is made the same way on purpose (0006:1365); a rotation makes the next one and publishes its hash (PM-0006-26, 0006:1364).
