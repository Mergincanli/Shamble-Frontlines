- F111 Entity groups and acks (ADR 0001:293-295: "splits by entity groups into datagrams that each decode alone, deltas against the same baseline, acknowledged per group"): recommend one baseline rule for U4: every group of tick T is a delta against one baseline B = the newest sent snapshot whose every group the client acknowledged (the Input ack = (16-bit low tick, group bitmask)); a partly acked tick is never a baseline; B older than the 32-entry ring (1.07 s) -> code against defaults. Events ride in exactly one group of the tick and are acked by that group's ack. Simple, loss-tolerant, and testable by L1 (-17 across loss, -18 baseline fallback bite). In SS the estimate fits one datagram most ticks (F112), so splits are rare; a unit test must force them.
- F112 SS snapshot estimate per client per tick (my arithmetic, proposed widths; U4 measures it): header ~12 B (type 1, 32-bit tick 4, baseline offset 2, newest-received seq 2, last-run seq 2, group 1); own state ~30-40 B when moving (pos+vel unquantised 24 B, weapon state ~7 B, stand-in attributes 8 B when changed); 47 remote soldiers x 60-bit delta = ~352 B; 4 very large units: hull+turret deltas and part health (parts rigid with the parent) ~20 B each = ~80 B (if every part's transform changed: 4 x 20 x 8.5 = 680 B, which with the rest breaks 1,000 B); projectile spawns 300 live / ~2 s mean life = 150/s = 5 per tick x 16.5 B = ~83 B, plus ends/blasts; cosmetic shot events 700/s / 30 = 23.3 per tick x 4 B = ~93 B; gameplay events ~20 B -> ~690 B per tick (cf. R2's 584/609 B, ADR 0001:705). Over WebSocket: + 1 B channel tag + 4 B frame header (126-65,535 B: RFC 6455 §5.2) + 22 B TLS 1.3 (RFC 8446 §5.2, AES-GCM) ~ 717 B vs fixes.rs's SNAP = 1,050 (fixes.rs:34). Not a measurement; U4's L1 B1 logs give the real mean (F99).
- F113 SS scene numbers U4 must fix as data and record (PM-0001-2, ADR 0001:1589; GLOSSARY.md:400-410): 48 soldiers 3 x 16 in one combat cluster in the centre field; 15 big vehicles: the 4 very large units (>=20 parts) in the fight, the other 11 moving elsewhere on the map; 300 live projectiles in the fight (trajectory records; spawn rate = 300 / mean life, recorded); 384 effect stand-in rows (8 per soldier) in the state and hash; hitscan 700 shots/s +-5 % (665-735/s): 48 soldiers firing continuously at the legacy 0.072 s interval give 666.7/s (inside by 1.7/s), at 0.06 s 800/s (outside), so the stand-in weapon interval should be ~48/700 = 0.0686 s in integer sub-tick units with remainder carried (ADR 0004 part 4), with a respawn rule that keeps the mean inside the band (deaths pause fire); doors 1 portal change per second near the fight; one destructible-wall stand-in; every client's set holds all 47 others on >=99 % of snapshots (region radius must cover the cluster). - F114 Determinism beyond npt-sim: npt-lab (runner, slot order) and the npt-server library pieces U4 runs on L1 (Decoder, I/O step, ConnLimits, AddrTable) have no clippy.toml (only client, l1, link, log, proto, room, sim have one: `ls crates/*/clippy.toml`), so a HashMap in them is allowed; any hash-ordered iteration there (e.g., the per-address table or pending pings) would make L1 same-seed runs differ (PM-0001-3's identity, -21's hash twins, plan §6.4:749-750). Recommend BTreeMap/slot-indexed Vec by rule in every code path an L1 run executes, and a twin test of the scenario runner (two processes, same seed, equal fate log and per-tick hashes) as the first L1 gate.
- F115 C1' makes npt-l1 event-driven: rule (b) ("lost once a LATER packet of its link and direction is acknowledged and 3 later are acked or 9/8 x max(srtt, latest) has passed", advisor-u3q.md:163-165) depends on packets sent after the lost one, which today's send-time model (send_stream, l1/src/lib.rs:651-711, arrival fixed at send) cannot know. U4's npt-l1 change therefore needs: (i) internal timed events (ack arrivals, loss declarations, PTO expiries, resends) processed in (time, fate index) order whenever any call's `now` passes them; (ii) outcomes independent of the poll pattern (a test: the same sends polled at different instants give the same fate log and arrivals; option A and B runs poll differently); (iii) one tie rule (an app send and an internal resend at the same ns); (iv) a way for npt-lab to step to the next event: `L1Net::next_event_ns()` (a method on a listed type, so no new symbol in §4.7) or a fixed fine step stated with its cost; (v) QUIC's single packet-number space: datagram packets' acks count as "later packets" for the stream's loss detection (RFC 9000 §12.3), which is what makes a single stream loss under 30 Hz traffic recover in ~9/8 RTT; (vi) F33's acks-in-bursts rule. L1 today has no next-event query (`grep "pub fn" crates/l1/src/lib.rs`: only connect, listener, with_fate_log, new, with_bite).
- F116 Input layout proposal (to replace the catalogue's 6 + 8 x 20 = 166 B with the codec's maxima, catalogue :95): header = type 1 B + ack (low 16 bits of the newest decoded snapshot tick, reconstructed against the room's tick; plus an 8-bit group mask) 3 B + count 1 B = 5 B; whole newest command = tick u32 4 B (or a 16-bit low half: the lead bound checks it anyway) + seq u16 2 B + move 2 x i8 2 B (length check in integers: x^2 + y^2 <= 127^2, exact on every target) + buttons u16 2 B + press counters 1 B per pressable button (u8 running totals; with 4 buttons 4 B; -58 wraps them) + aim point 44 bits (E3's 16+16+12 at 1 cm, within the 80-bit limit: ADR 0001:226-227) 5.5 B + view time (16-bit tick offset back from the command tick + 8-bit fraction) 3 B = ~22.5 B -> 23 B; a repeat = 1 B change mask + tick delta (1 B, since ticks may skip under OQ-0001-6 (b)'s re-align) + changed fields, worst case 2 + (23 - 6) = 19 B <= the whole command (the catalogue's "never larger" rule). Max datagram = 5 + 23 + 7 x 19 = 161 B (<= 166 B; + 57 B IPv4 overhead = 218 B at the cap, typical P2 datagrams ~40-60 B). Proposed, not measured; U4 states its own table and the limit test reads it.
- F117 Two clocks on the client, kept apart: (1) the command clock: the server-time offset from the client's own Ping/Pong samples (ADR 0001:239-242; Quake III rules: drift <=1-2 ms per frame, halve errors >100 ms, reset >500 ms), judged by -47 (<=5 ms at 2 s, P2) and driving which tick a command is stamped for (OQ-0001-6's lead); (2) the interpolation clock: newest snapshot tick advanced by the local clock since its arrival stamp (ADR 0001:332-334), minus the adaptive delay, which must be monotonic and rate-slewed (never stepping back) or -45 and -61 count spurious extrapolation and misplaced events. -47's bite "newest raw sample" fails because one P2 sample's offset error is (jitter_up - jitter_down)/2, up to +-10 ms (my arithmetic), so a filtered estimator (lowest-RTT samples) is needed; ping rate as data, within the room's 10/s limit (catalogue :99).
- F118 -45's bite "a snapshot buffer one slot too short for P2" presumes the Interp buffer is sized in slots by a stated rule: proposed slots = ceil(max delay 5 intervals + extrapolation 1 interval) + 1 for the snapshot being written = 7 (at 30 Hz), the bite using the P2-derived size minus one; state the rule so the bite is meaningful.
- F119 EventQueue rule for -22 (catalogue :106 Kick overflow; ADR 0001:301-302): bounded per client (cap as data); on overflow the room forces one resync (FullState clears the queue: Q8 approved) and, if that FullState is not acknowledged within a bound (data, e.g., 60 ticks) or the queue overflows again inside it, sends Kick(overflow) and drops the client; a never-acker otherwise keeps getting FullStates forever (one in flight, each never acked): the bound makes "resynced or dropped" finite. - F120 What the room needs from npt-server per client per tick on L1 (plan §4.4:505-506) maps to Link: arrival-stamped decoded messages; rtt (Link::rtt_ns after C2); loss (C3's new Link::loss, L1 from implicit acks over a window, integer units, None on WS); send-buffer space (§4.4; L1 has no cwnd: report "unbounded" explicitly, not a number L1 does not model); max datagram size (L1's connect value: choose 1,200 B so the 1,000 B encoder cap never meets TooLarge); unsent count (0 on L1). - F121 SS event volume (my arithmetic): 700 hitscan shots/s; if about half hit, ~350 hit events/s are gameplay events (ADR 0001:297-302: hits, deaths, kills resent until acked) relevant to nearly every client in the one cluster. At P2 each event is resent until the ack covers it, ~(RTT + buffer + tick) / tick = 5-7 snapshots, so ~12 new hits per tick x ~5 B x ~6 sends = ~350 B per snapshot of event section, on top of F112's ~690 B: SS sits at the 1,000 B datagram cap and the 1,067 B window, so the priority accumulator must budget events with entity records (resend each event at most every k ticks, or once per RTT). - F122 -17's server-side hash must be the per-client mirror, not the world: with the priority accumulator a relevant entity may skip up to 3 snapshots (ADR 0001:405-407), so the client legitimately holds an older value; hashing "the server's quantised state for that tick" (ADR 0001:1605) literally would mismatch by design. - F123 Lag compensation across the seam: hitscan resolves inside the sim step (ADR 0001:621-623), but whether a command fires depends on sim state (cooldown, ammo), and HitHistory/rewind_at are npt-room's (plan §4.7:576-577).
