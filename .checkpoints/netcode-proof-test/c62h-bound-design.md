## Block 1: facts from the code (done)
- L1 datagram fate is decided at send, in `Net::datagram` (l1/src/lib.rs:1079-1172): Burst if in a burst (:1097-1098), Lost by the loss draw (:1099-1100), else Delivered{arrival} (:1101-1104); one fate entry pushed per datagram (:1106-1117). The reorder step may later move a *held* datagram's arrival to next arrival + 1 and set overtaken (:1134-1146), never to Lost. A send on a closed link pushes no entry (:1084-1086); too large takes no index (:1087-1089).
- Fate entry fields (l1/src/lib.rs:306-321): link, dir, carries (Datagram / Stream{channel,pn,message,part,parts} / Ack), seq, sent_ns, len, outcome, overtaken, retransmits. No tick, no slot. FateLog entries are private; public API is len, is_empty, for_each_canonical, reorder_counts (:332-438) and L1Net::with_fate_log (:1885-1887).
- Recv to the client carries channel, bytes, arrival_ns only (l1 :1676-1680): no fate index.
- Lab send path: after each room tick, per slot: take_datagrams (room.rs:595-601: "the datagrams (snapshot groups) the last tick coded for slot, in group order"), take_control, then Server::send (scenario.rs:557-584) -> send_unreliable per group (:569-571), send_reliable per control msg (:572-574). Pings are sent by the pump inside Server::io (scenario.rs:458-545), never inside Server::send. So the Down datagram entries pushed during one Server::send(slot) call on that slot's link are exactly that tick's snapshot groups.
- Link id = connect order index (l1 :1015); lab connects in `order` = slot order (scenario.rs:780-788, :845-846; only a bites test build shuffles it).
- Room: server_hash Some iff the room coded a snapshot or a full state for that client at that tick (room.rs:204-208, :299-300 reset each tick; set at :1128 full state, :1357 snapshot). None on: full state in flight (:1087-1089, NC-L10's gap), budget short (:1173-1176, :1201-1204), encoder refusal (:1343-1346; full state :1119-1122), kicked (:1047-1049, :1057-1063). Room log writes hs.server_hash per slot each tick (logs.rs:534-564).
- Client files lost only in `see` (client/src/lib.rs:583-615): a tick leaving the 32-tick ring unfiled, or a jump past the ring. Every decode failure files the sentinel, never lost (:717-807). A group of a tick >= 32 behind newest is dropped as stale (:527-552) and that tick was already resolved.
- ACK_RING_TICKS = 32 at 30 Hz, about 1.067 s (sim/src/ticks.rs:58-70); FULL_STATE_ACK_TICKS 60 (:49-56).
- Lab writer: Res Open/Hash/Lost (logs.rs:123-129); lost after a hash is ignored, hash after lost overrides (:368-388); snap_incomplete 1 iff Res::Lost (:442); stop decides open ticks inside a span lost (:727-748) but on a measured run every measured tick is resolved before the stop (scenario.rs:1126-1137: the run fails at the after cap otherwise).
- Judge: a series check sums the values (eval.rs:282) over the window (:120-126); an empty tick series is a gap, not a pass (:314-327); a gap with no failing check makes the run INVALID (:1215-1231). Bite status is Shown only if every bite run is shown (eval.rs:1489-1496); bites can be expect-invalid with a named validity rule (marks.rs:127-138). Figures are listed in figures.rs:632-825; `decoded` already joins room server_hash, client decoded_hash and snap_incomplete (figures.rs:316-456).

## Block 2: can "too late" happen on L1? (done)
- A datagram's delay is at most one_way + half_jitter (P3: 75 + 15 = 90 ms; l1 :215-221, :790-814), and the reorder step holds one at most until 1 ns after the next one's arrival (l1 :1134-1146), so any snapshot datagram arrives within about 180 ms of its send on P3 (P2/B1 less). A datagram of tick k+32 is sent 1.067 s later and takes at least 60 ms. So no snapshot datagram can arrive after one of a tick 32 newer: ring-lateness cannot occur on P0-P4 or B1.
- A full state: while one is in flight the room codes nothing for that client (room.rs:1087-1089), so nothing newer can overtake it.
- So the client's stale path (client lib.rs:527-552) cannot fire legitimately on L1; it is 0 on every judged run (advisor-c62h-review-full.md:46).
