# netcode-proof-test: plan review round 1 (revision 1), findings as returned (compact copy for revision 2)

## security-auditor: REVISE (19 findings)
- **F1 Critical** (4.2 E11/E15, 4.3 spike-only controls, 11 item 3 (record form)): Nothing authenticates the spike-only controls (SetProfile, SetRewindCap, TriggerBurst, BlockUdp), the panic injections for -26 and -59, or the checklist record form. All of them travel on the public game protocol from the overlay. Exploit: a prober who found rs.nt in CT joins and sends SetRewindCap(max) or BlockUdp, or posts 'achieved' to the form. The room's lag-compensation cap, profile or transport then changes mid-run, and PM-0001-48, -49 and -53 come out silently wrong. It also lets anyone buy extra rewind. **Change:** Add to 4.2 and the catalogue: (1) room-wide controls (rewind cap, cap raise) and panic injections only through a local control socket on RS (a Unix socket, driven over SSH by the laptop session), never as a network message; (2) per-session controls for Mustafa's own session (profile, B1, UDP block, the record form) only with a per-run control capability: random 128-bit, minted on RS, handed over in the URL fragment, compared in constant time, acting on the sender's session only; (3) every control and form record logged with its source; npt-judge marks a run INVALID if any control arrived without the capability; (4) a bite: a control or form post from a plain join is refused and counted; (5) the catalogue gives each control its channel and its authority.
- **F2 High** (7.3 steps 2-3): The firewalls are applied after the VMs are created, so each VM boots unfiltered on IPv4 and IPv6 until Mustafa attaches them. That exposes sshd and anything cloud-init starts: the exporter, TCP 80, the page host. **Change:** Reorder 7.3: (1) set the operator's source in both firewall objects; (2) create LG with LG's firewall chosen in the create form; (3) set RS's 9100 source to LG's IPv4; (4) create RS with RS's firewall chosen in the form; (5) extra CAX21s the same way. Add label selectors (role=rs, role=lg) as a second binding. cloud-init loads nftables (default drop, table inet) before it starts any service.
- **F3 High** (10 (join tokens), 8.4 (public names)): The plan says the test join tokens keep strays out, but it never says how a browser or the macOS runner gets a token. If the page host hands them out, anyone who finds rs.nt joins a measured room. N becomes 49 and the bandwidth and tick marks are wrong. Exploit: read CT, open the page, join. **Change:** Specify in 10: (1) tokens are minted per participant on RS and delivered out of band: bots by file over SSH, browsers in the URL fragment from the laptop session, the runner a single-use token per dispatch that is treated as public; (2) each token is bound to one room and expires at session end; (3) rooms refuse joins beyond the planned N; (4) the page host never mints tokens; (5) refused and stray sessions are counted per run; (6) a measured run that admitted any session outside its roster is INVALID.
- **F4 High** (1.6, R-4): The host-key options have order and binding flaws. (1) Option 1 needs the production certificate, but VS1's first issuance goes to staging, which browsers do not trust, so RS's first check has no path. (2) Nothing ties the fetched name to the IPv4 Mustafa read in the console: a typo or a stale record means the file comes from someone else's VM. (3) cloud-init makes rsa, ecdsa and ed25519 host keys by default. (4) The console option: /etc/issue is written late (runcmd), possibly after getty has drawn its prompt. Comparing 43-character fingerprints by eye across up to 5 VMs per session invites prefix-only checks. **Change:** RS: HTTPS-published, from the production certificate only. Set ssh_genkeytypes [ed25519]. The file holds full known_hosts lines, is root-owned 0444 and is written after cc_ssh. The laptop checks via DoH that rs.nt's A record equals the console IPv4, then fetches with normal TLS verification. It confirms the served certificate is today's (notBefore after RS's creation, present in CT). It then connects to that IPv4 with HostKeyAlias, StrictHostKeyChecking=yes and a per-session known_hosts file. Fallback, and VS1's staging day: the console, comparing the full string, which the laptop prints in groups of 4. LG: no lg.nt name and no console check. LG's SSH rule source becomes RS's IPv4, and LG is reached by ProxyJump through the verified RS (RS sshd: TCP forwarding with PermitOpen <LG>:22 only). LG's key is then learned over Hetzner's internal path, and LG has no SSH facing the internet.
- **F5 High** (12.3, R-23): The laptop session's rules exist only in a prompt. (1) The repo settings allow `git push origin claude/*` without a prompt, so it can push to the change-set branch (claude/netcode-proof-test-plan-hcky5g) despite 'never pushes'. (2) Its credential is Mustafa's full GitHub account: main is protected, but other branches and green PRs needing 0 approvals are reachable. (3) The guard fails open in a day session if it cannot load, and it is untested on Windows. (4) It reads text attackers can influence (server logs with client strings, scanner request lines, VM output) while it holds a shell on his personal laptop, SSH to the VMs and push rights. That is a prompt-injection path. **Change:** Write into 12.3 and ops/operator/: (1) the main folder is a clone on main; the run commit and the results branch live in worktrees under .gate/; (2) Manual (default) permission mode, never auto or bypass; (3) an extra `--settings ops/operator/settings.json`, reviewed at stop B, that denies every push except `git push origin HEAD:claude/npt-results`, denies gh, WebFetch and WebSearch, and denies reading the key file; (4) RS logs never carry client-supplied strings verbatim (a length or hash, or escaped and cut to 64 B); (5) the session reads npt-judge's summaries rather than raw logs and treats VM output as data; (6) WebDriver uses fresh temporary browser profiles, never his own; (7) VS1 step 0 proves on Windows that the guard loads and that a push to the change-set branch is refused.
- **F6 High** (1.5): `ssh-keygen -t ed25519 -C npt-operator` has no -f and no -N. It writes or overwrites ~/.ssh/id_ed25519, his default identity, which is offered to every host. It also prompts for a passphrase that a non-interactive shell cannot answer. And 'never in a chat or a paste' leaves out the real leak: any tool output of the private key enters the transcript and goes to the API. As written it does not meet SPIKE_PLAN:154-156. **Change:** (1) `ssh-keygen -t ed25519 -f ~/.ssh/npt_operator -N "" -C npt-operator`. No passphrase is acceptable because the key opens only the spike project's throwaway VMs, from one source address. Alternatively Mustafa loads a passphrase key into ssh-agent himself. (2) The session prints only the .pub and the fingerprint, and never opens the private file (the repo's Read(~/.ssh/**) deny covers this when settings load). (3) An ssh_config block with IdentityFile, IdentitiesOnly yes, ForwardAgent no and a per-session UserKnownHostsFile. (4) At the change-set's close, remove the public key from the Hetzner project and delete the file. (5) Make a new key if the private key is ever shown.
- **F7 High** (4.2 E21, 8.1 (TCP 31000)): npt-host is new code that faces the internet, serves files and holds the TLS key, yet it is outside E14's hostile set. A path-traversal or directory-listing bug would leak the TLS key, which lets someone impersonate rs.nt, its cert-hash file and its host-key file for the certificate's life. The canaries could leak the same way. No headers are set beyond COOP/COEP. **Change:** Add to E21: (1) a compiled-in allow-list of paths from a dedicated dist directory (index, JS, Worker, Wasm, cert-hash.json, ssh-host-keys.txt); GET and HEAD only; no listing; never the clone, .git, logs, results, canaries or keys. (3) Limits: a 5 s header timeout, an 8 KB header cap, per-address and total connection caps. (4) E14's slow-loris and flood also hit 31000. (5) A bite: /../Cargo.toml, %2e%2e and /npt/ must answer 404. (6) RS's Origin allow-list is exactly the page origins, with no localhost and no null; the Safari runner loads the page from RS.
- **F8 High** (1.3, 4.4, 10 (cloud-init), 12.3 (rebuild)): There is one unprivileged user, and it is also the SSH login. runcmd runs as root, so the clone and `cargo build` (every crate's build scripts and proc macros) run as root. Room processes that parse hostile input could rewrite the binaries or ~npt/.ssh/authorized_keys, which contradicts B12's interim position. Password login is not off by default (ssh_pwauth 'leave the value unchanged'). Nothing checks the pasted file. **Change:** (1) Users: npt (login; sudoers for a fixed command list only), npt-build (clone and build), npt-room (rooms; no shell; no write to the binaries or the clone), npt-host (page host and ACME). (2) Set `ssh_pwauth: false`, `disable_root: true`, `ssh_genkeytypes: [ed25519]`. (3) An sshd_config.d drop-in: PasswordAuthentication no, KbdInteractiveAuthentication no, PermitRootLogin no, AllowUsers npt, AuthenticationMethods publickey, X11Forwarding no, AllowAgentForwarding no, MaxAuthTries 3, LoginGraceTime 20. (4) nftables first. (5) rustup-init by a pinned SHA-256 per architecture (two values). (6) As npt-build: `cargo fetch --locked`, then `cargo build --locked --offline`; 12.3's rebuild the same way. (7) No curl | sh and no #include URL. (8) Security upgrades at creation; unattended-upgrades and reboots off during runs. (9) The run plan prints each cloud-config file's SHA-256. The laptop's first command on each VM compares the stored user data's hash and `git rev-parse HEAD` with the run's values, and stops on a mismatch.

## engine-architect: REVISE (14 findings)
- **EA-1 High** (4.1 Layout (plan:164), 4.2 E2-E5/E11 (plan:189-198), 4.3 npt-room (plan:225-226)): npt-room is one binary that does two jobs. It holds the room's match logic: slots, command checks, input buffer, interest, lag compensation and per-client encoding. It also holds the room process: the S17 loop, threads, async I/O, transports and metrics. ADR 0002 part 3 keeps these apart. `room` has no I/O, no async runtime and no clock, its timers count ticks, and it builds for wasm32 and natively. `server` is the shell that reads `Instant`. Merging them breaks three things. (a) L1 has to run 'the real server code in one process', and another crate cannot import a binary's items. (b) The boundary spike's 10-minute match runs in local mode, with the Worker hosting the local server, so the stand-in room logic must build for Wasm. That is impossible if the logic is tied to tokio and threads. (c) ADR 0002 says which timers are tick-counted in `room` and which run on wall time in `server` (the join deadline, per-connection limits). The plan never says this for its own checks. **Change:** In 4.1 and 4.3, split the crate in two. `npt-room` is a library: slot table, per-client command queues and the server checks of E3 (both OQ-0001-6 options), the input buffer, interest (E5), hit history and the rewind query (E11), per-client delta encoding and the event queue (E4). It has no I/O, no async runtime and no clock reads, its timers count ticks, and it builds for wasm32 and natively. `npt-server` is the binary: the S17 loop, the tick thread and its pinning, the I/O runtime and transports, the per-connection wall-time limits (Join deadline, handshake cap, per-address caps), metrics, and the panic catch that sends RoomEnded(crash). Add one table that places each E3, E4 and E6 check in room (ticks) or server (wall time). Add a U4 check that runs `cargo check --target wasm32-unknown-unknown -p npt-room` and a `cargo tree` test showing npt-room has no tokio, quinn or tungstenite.
- **EA-2 High** (4.1 crates/net (plan:162-163), 4.3 npt-net (plan:220-224)): The thin transport interface (`Link`, `Listener`) sits in npt-net, next to quinn, wtransport, web-transport-quinn, tokio-tungstenite and L2. In ADR 0002 and ADR 0001, the Rust side of that interface lives in `protocol`, together with a loopback backend. `protocol` has no transport crate, has no async runtime and builds for Wasm. L1 plugs in behind it. The plan has three gaps here. There is no loopback backend, which the boundary spike's local mode and ADR 0001's foundation milestone need. Any crate that uses `Link`, such as npt-client for the bots, picks up the transport dependencies, yet npt-client must build for wasm32. The plan never says whether `Link` is async (tokio) or poll-based, and L1 on simulated time needs a synchronous, poll-style interface or a deterministic executor. Also, the symbols list has server adapters only (`WtServer`, `WsServer`), while E12's native bots need WebTransport and WebSocket clients. **Change:** Move `Link` into npt-proto, or into a leaf `npt-link` crate with no dependencies. Make it poll-based: send and receive bytes with explicit timestamps, return the link state and the RTT, and take a named channel for reliable sends, as ADR 0001:432 says. Add a `Loopback` backend beside it. L1's `L1Net` implements `Link` in a crate that has no transport dependencies. npt-net keeps only the native adapters, `WtServer`/`WtClient` for both WebTransport crates (one feature each) and `WsServer`/`WsClient`, plus L2 (`ImpairSocket`, `TcpDelayProxy`). Add the client adapters to 4.3. State that npt-client never depends on npt-net.
- **EA-3 High** (4.2 E2/E15 (plan:189, 202), 4.3 (plan:222, 225), 6.4 (plan:334)): The plan has no home for the code that drives L1, or for its simulated clock. L1Net sits in npt-net. npt-net cannot depend on the room or the client, because they depend on npt-net, so that would be a cycle. That leaves nowhere for the scenario runner that steps one server and 48 clients on one simulated clock. `run_tick_loop` is the S17 loop and reads a monotonic clock (E2, E18). No `Clock` trait or `now` parameter appears in the symbols, so L1 cannot run the real loop or the server's wall-time checks on simulated time. The step order inside one simulated instant (deliver packets, server tick, clients) is not fixed either, yet PM-0001-3's identical fate logs and hashes depend on it. PM-0001-30's bite ('a wall-clock read on one transport's command path') shows the drafts treat a wall-clock read in the command path as a defect class. **Change:** Add a crate `npt-lab`, the analogue of ADR 0002's devtools. It may depend on everything and nothing depends on it. It holds the L1 scenario runner: one simulated monotonic clock (integer ns, `SimClock`) and a fixed step order per instant (due packets in fate-log order, then the server tick if due, then each client in slot order). It also holds the 48 headless clients' wiring and the seed plumbing, plus the x86-64 replay tool (see EA-11). In npt-server, write the S17 policy as a pure function, `due_ticks(now, schedule) -> (to_run, dropped)`, with the cap derived from the tick rate (EA-9). Unit-test it in this container on a fake clock with PM-0004-67's three bites (timer-period counting, uncapped catch-up, an uncounted drop) before any VM hour. Feed the server's wall-time limits from an injected `now`, so the L1 hostile-input rows (-21, -22) run on simulated time. Add `SimClock`, `MonoNow` (or a `now_ns: u64` parameter), `L1Scenario` and `due_ticks` to 4.3.
- **EA-4 High** (4.2 E7 (plan:194), 4.3 npt-client and web (plan:228-230), U7 (plan:542)): U7 claims 'a Worker host in ADR 0002 part 5 and 6's shape', but neither E7 nor the symbols say what that shape is. So the boundary spike may end up measuring code it will not keep. The netcode-architect digest's E7 has two items the plan dropped: 'host passes datagram arrival times in (endpoint reads no clock)' and 'page posts newest input + cursor ray + view time per frame'. Also missing: a bindings-only crate separate from the client endpoint (the counting build wraps every export, so the export set must be small); the export surface (create, mode flag, one input call per tick carrying the page input, each datagram with its own arrival stamp, the previous send time and the host's current time; one step call returning where the datagrams and the block lie and when the next tick is due); the host setting its timer from that value, with at most 7 ticks per wake; a fresh `memory.buffer` view after each call; the aim cast in the Worker against the state published for the page's view time (-51); and the block writer (one transferred block per tick, with the page keeping the two newest). web/ has no `net.ts`, which would hold the Worker's WebTransport and WebSocket backends with the 1.5 s fallback, `maxDatagramSize` polling and arrival stamping. **Change:** Write E7 out as a list, and add these symbols. `npt-client` is a library with no bindings, no transport and no clock: `ClientEndpoint::input(page_input, datagrams: &[(bytes, arrival_ms)], prev_send_ms, now_ms)`, `ClientEndpoint::step() -> StepOut { datagrams, block, next_due_ms }`, `AimCast`, `BlockWriter` with one layout table. `npt-client-wasm` holds the wasm-bindgen exports only (create, mode, input, step). For web: `net.ts` (WebTransport first, 1.5 s timeout, then WebSocket, `requireUnreliable`, `maxDatagramSize` every 10 s, `performance.now()` stamped in each datagram's own event), `host.ts` (timer from `next_due`, catch-up of at most 7 per wake, fresh memory view per call), `block.ts` (the page's typed-array views, two newest blocks). State these design rules: no per-entity call, at most 4 Wasm calls per tick, the page never touches a packet. They are counted later by the boundary spike and not judged here.
- **EA-5 Medium** (2 Out of scope (plan:128-130), 4.2 E7): The plan lists the boundary spike's marks as out of scope, but not the decisions and measurements left to it, so the harness could pre-empt them silently. The biggest gap is types. The plan never says how TypeScript gets the message, control and block types. Building ts-rs or the layout generator now would pre-empt the boundary spike's item 4 and adds a feature nothing in this test needs. Hand-writing them is fine, but should be said. The same goes for B2 only (no B3 ring), no counting build, one Wasm instance, online mode only (OQ-0002-3 and local mode are the boundary spike's, see EA-1), and S18 pacing built to the rule but not judged. **Change:** Add a bullet 'Left to the boundary spike' to §2 Out of scope. It should say: TypeScript types for the stand-in block, controls and messages are hand-written, with one layout-version constant checked at start, and no ts-rs or layout generator (PM-0002 item 4). B2 only, with no B3, no SharedArrayBuffer and no counting build. One instance, online mode only, with the room core kept Wasm-buildable (EA-1).
