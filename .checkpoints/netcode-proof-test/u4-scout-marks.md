## Sources read (summary per source, as read)
- S-RFC9002 (www.rfc-editor.org/rfc/rfc9002.html, fetched 2026-11-09): §5.1 an RTT sample only when "the largest acknowledged packet number is newly acknowledged" and "at least one of the newly acknowledged packets was ack-eliciting"; §6.1.1 kPacketThreshold 3; §6.1.2 time threshold max(9/8 x max(smoothed_rtt, latest_rtt), kGranularity = 1 ms); §6.2.1 PTO = smoothed_rtt + max(4 rttvar, kGranularity) + max_ack_delay, scheduled at each ack-eliciting send, doubled at each expiry, reset by an ACK (with a client address-validation exception); max_ack_delay applies to Application Data (App. A.8). Sure: high (spec text). C1' (b)-(c) and C2 match it; C1' (b) omits the 1 ms kGranularity floor on the time threshold (minor).
- S-HashMap (doc.rust-lang.org std HashMap and RandomState, fetched 2026-11-09): "The algorithm is randomly seeded"; "each HashMap instance uses a different seed"; iteration "in arbitrary order". Nothing on per-process seeding or on platforms without randomness. Sure: high on what the docs say; the docs do not promise that two native processes iterate a map differently, nor what wasm32-unknown-unknown seeds with, so the hash-map bite must be shown to change state, not assumed.
