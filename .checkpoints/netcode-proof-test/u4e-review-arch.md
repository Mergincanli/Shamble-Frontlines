## Findings (a line after each)

**A1, Medium, fix before merge: the room's reliable outbox leaves encoding and the channel to every caller.** `Room::take_control` returns typed `Message`s (room.rs:576-584), while `take_datagrams` returns bytes. The room already encodes each FullState once, with its own `Quant`, to count a refusal (room.rs:1075-1079), then throws the bytes away; the caller encodes again. In the only caller, the test lab (server/tests/common/mod.rs:274-281), that second encode uses `npt_proto::encode` (the default Quant), and the channel is looked up by type name. Consequences: (1) every FullState is encoded twice; (2) under an npt-proto bite forwarded through `Room::with_bite` (room.rs:480-491: "whose Quant the room's encoder then codes with"; the -57 bites coarsen every packed record, quant.rs:16-22), the snapshots go out bitten and the full states clean; (3) plan.md:508-509 ("Encoding stays on the tick, as -6's share") is left to each caller, and U4r's lab and U6's TickLoop each re-implement the encode and the channel choice. Fix: `take_control` hands out the bytes the room encoded on the tick with its own Quant, and the caller reads the channel from the type byte's row of `Limits::TYPES` (npt-proto's documented rule, limits.rs:55). Cheapest proof: in a bites-build test, `Room::with_bite("PM-0001-57/pos-4cm")`, join one client, and compare the FullState bytes the lab sends with the room's own encode of the same message: they differ.

**A2, Medium, fix before merge: the pump picks the RTT source by whether the link answers, not by the session kind §4.9 names.** `Decoder::rtt_ns` is `link.rtt_ns().or_else(|| lowest ping sample)` (pump.rs:264-269), and `Decoder::new` takes no session kind (pump.rs:203-209). §4.9 (u4-build-plan.md:350-353): "for a wt or L1 session the link's rtt_ns, for a ws session the lowest recent sample of the server's own pings ... The pump knows each session's kind from the listener that accepted it". The Link contract is "the backend's smoothed round-trip estimate" (link/src/lib.rs:79-81). So a WebSocket Link that reports TCP's srtt (npt-tcpinfo's srtt exists for WsServer) would feed U4h's tolerance and -50's WebSocket leg TCP's estimate, not the ping samples. And a wt or L1 session uses ping samples until the link's first sample, so one session mixes two sources. The only ping-path test uses a link that answers None (server/tests/pump.rs:228-241, `NoRtt`). Also, the builder's record says the pump's per-tick report to the room carries the RTT (u4e-build.md:22-23), but `Room::pump_report(slot, sent_bytes, max_datagram)` has none (room.rs:669). That is right at U4e (the RTT's consumer is U4h's tolerance), but the report must not repeat the record's line. Fix: `Decoder::new` takes the session's kind (or one flag: RTT from the room's pings), and `rtt_ns` chooses by it; add a test with a link that answers Some for a ws-kind session. Cheapest proof: a pump test with a link whose rtt_ns is Some(x) and one Pong sample y ≠ x, which shows rtt_ns gives x where §4.9 asks for y.

**A3, Medium, route (not before merge): the client's 32-bit event-number rebuild has no anchor in the protocol.** The endpoint rebuilds each event's 16-bit number near `event_near` (client lib.rs:606-616). That value comes only from configuration, `with_starts(_, event_start)` (lib.rs:280-286; default 0). `JoinAccepted` (proto msg.rs:94-107) and `FullState` (snapshot.rs:630-638) carry no event counter, and the room numbers every event room-wide (room.rs:776-779). So a client admitted after the room's counter has moved 32,768 or more from the configured start rebuilds every number wrong. `client_hash` hashes 32-bit numbers (§4.6), so its decoded hash mismatches on every tick that carries an event: a correct build fails -17. This is the case of -19's late join (C-U6-11) and of every rejoin after a Kick or a replacement. At U4r every client is admitted in the warm-up (carry 62 (d)), so the judged runs are safe only if the lab gives each client the room's start and admits all of them before the counter moves. Fix: a protocol field (JoinAccepted or FullState carries the room's next 32-bit event number). That is npt-proto and the catalogue, not U4e's lane, so it goes to the advisor as a carry for U6, and U4r's brief states the warm-up condition. Cheapest proof: a Loopback test that admits one client after the room has stamped more than 32,768 events and compares its filed hashes with the room's.

**A4, Medium, fix before merge: `Room::tick_input()` does not return the tick's input.** Its doc says "what a recording holds" (room.rs:551-554). But `tick()` clears that tick's spawns, teleports and attribute changes right after the step (room.rs:780-782), and `script()` writes the next tick's into the same field (room.rs:587-599). After a tick, it returns that tick's commands with no scripted inputs, or with the next tick's, so one field holds two ticks' state. A recorder reading it (U4r's `scenario --record`, A12's one replay driver) replays without the teleports and attribute changes. Fix: keep the pending script in its own field and move it into `input` in `fill_input` (or clear the scripted lists at the start of the next tick). Cheapest proof: a room test that scripts one teleport for tick t, calls `tick()`, and asserts `tick_input().teleports` holds it.

Nine have no consumer in any test, plan line or ruling: `Roster::new` (Room::new builds the roster itself, room.rs:425), `Roster::is_bound`, `Decoder::limits`, `Decoder::is_joined`, `ConnLimits::join_deadline_ns`, `ClientEndpoint::closed`, `ClientEndpoint::unknown_pongs`, `ClientEndpoint::with_lead`, and `ClientSlot::skipped`. `Room::with_cover` has a plan reason (§4.9's two cover variants) but no test (§4.11's T17 rule). Fix: make the nine pub(crate) (or name their consumer), list the rest with reasons in the report for the advisor, and bring §4.1's npt-room, npt-server and npt-client rows up to date in the merge commit, as W1-PUB and B5 did.

**A6, Medium, route (not before merge): a session's life is split between the room, the pump and the caller, with no library path to end a session.** The room decides a replacement (room.rs:601-606: the old connection "then gets Kick(replaced) from the caller") and a Kick(overflow) (room.rs:308-313). But `Decoder` has no way to close a session or send it a Kick: it has only `accept` and `reject` (pump.rs:236-256), and `send_control` is private. The only driver (server/tests/common/mod.rs:229-287) ignores `replaced` (`Ok((slot, _))`, :241) and never closes a kicked session. So in it, a replaced session's Inputs keep reaching `room.receive` under the slot the new session now holds. U4r's lab and U6's TickLoop will each write this glue from scratch, and nothing in U4e proves it. Fix: `Decoder::close(link, Kick, now)`, plus the drive rules written once: either a small driver in npt-server's library (a new pub item, for the advisor) or U4r's brief copying tests/common's order with these two gaps closed and a test of each. Cheapest proof: a Loopback test where a second endpoint joins with slot 0's token and bind while the first is live, and the first keeps sending Inputs.
