- F3.4 Time: quinn stamps every received datagram with `endpoint.runtime.now()` taken at the start of the driver's poll (endpoint.rs:375, passed into `endpoint.handle(now, meta.addr, meta.dst_ip, meta.ecn, ...)` at :802-809); connections stamp sends with `self.runtime.now()` before `poll_transmit` (connection.rs:1017-1035). TokioRuntime::now() = `tokio::time::Instant::now().into_std()` (tokio.rs:37-39): std's monotonic clock unless tokio time is paused (needs tokio's test-util, not in the workspace's tokio features). So a datagram an ImpairSocket hands to quinn at its due time is stamped as arriving then, and one quinn hands over is stamped as sent before the delay: both endpoints' RTT samples (`rtt = now - largest_acked_packet_sent`, ack delay subtracted: quinn-proto-0.11.19/src/connection/mod.rs:1538-1548, paths.rs:335-347) include the injected delay exactly like a network's. HIGH.
- F3.5 Receive loop rules (quinn endpoint.rs:775-848): buffers are BATCH_SIZE (= 32 on Linux, quinn-udp unix.rs:806) iovs, each `max_udp_payload_size.min(64K) * max_receive_segments` bytes (endpoint.rs:750-760; default max_udp_payload_size 1500-28 = 1472, quinn-proto config/mod.rs:60); quinn splits each buffer by `meta.stride` (:800). `Ready(Err(e))` other than ConnectionReset ends the EndpointDriver and with it every connection (:839-845, logged at :152-156); `Ready(Ok(n))` loops straight back into poll_recv until the WorkLimiter stops it (:794-853), so `Ready(Ok(0))` would spin. So ImpairSocket's poll_recv: fill at most min(bufs.len(), meta.len()) due datagrams, one per iov, `len = stride = n`, real `addr`, pass-through `ecn` and `dst_ip`; else store the waker and return Pending; never Ok(0); never an error for an empty queue. HIGH.
- F3.6 Send loop rules (quinn connection.rs:1016-1081): `max_datagrams = socket.max_transmit_segments().min(10)` (:1020-1023); quinn calls `io_poller.poll_writable(cx)` BEFORE every `try_send` (:1048-1052), and on WouldBlock keeps the transmit and loops back to poll_writable (:1059-1069); any other error kills the connection driver. Endpoint-level replies (version negotiation, refusals, stateless resets, retries) call `try_send` directly and drop on error (endpoint.rs:563-585). With `max_transmit_segments() == 1`, quinn-proto produces one datagram per Transmit and `segment_size: None` (quinn-proto connection/mod.rs:466-470, 1011-1014). HIGH.
- F3.7 The real socket quinn would use (TokioRuntime::wrap_udp_socket, tokio.rs:30-35) is `tokio::net::UdpSocket` + `quinn::udp::UdpSocketState`; `UdpSocketState::new` sets the socket non-blocking (quinn-udp unix.rs:109), turns on UDP_GRO on Linux (:129) and DF / IP_PMTUDISC_PROBE / IPV6_DONTFRAG (:131-139, :178-184), so may_fragment() is false on Linux (:283-285) and quinn runs MTU discovery (upper bound 1452: quinn-proto config/transport.rs:750; start 1200: lib.rs:332). GRO delivers up to 64 datagrams per buffer (unix.rs:1010-1028: "this MUST be set to UDP_GRO_CNT_MAX"). HIGH.
- F3.8 tokio's timer cannot meet the advisor's 0.25 ms release-precision condition: `Sleep` "operates at millisecond granularity and should not be used for tasks that require high-resolution timers" (tokio-1.54.1/src/time/sleep.rs:12-15), and deadlines are rounded up to the end of the millisecond (runtime/time/source.rs:17-20: `instant_to_tick(t + Duration::from_nanos(999_999))`). A release driven by tokio::time is late by 0 to 1 ms plus the wake-up, by construction. The release clock must be a dedicated OS thread (std `Condvar::wait_timeout` or `thread::park_timeout`, optionally a short spin for the tail); U3 measures it. HIGH (tokio fact); the thread's precision on RS is unmeasured.
- F3.9 quinn's own timers stay on tokio (1 ms, TIMER_GRANULARITY 1 ms in quinn-proto lib.rs:334) in production and in L2 alike, so they are not a difference L2 introduces. Loss detection: packet threshold 3, time threshold 9/8 RTT (quinn-proto config/transport.rs:382-383; connection/mod.rs:1692-1725). HIGH.

### Q5 (PM-0001-23, -24; R-17): done
- F5.1 The rows (docs/adr/0001-multiplayer-netcode.md:1561-1562): -23 throttles the link to 128 kbps for 10 s, 10 throttles per run, P2 otherwise; -24 puts a bottleneck at 50 % of the snapshot stream's rate for 10 min per controller (NewReno, Cubic) at P2. Both: "The drop-tail queue holds at least 4 full datagrams (about 4.1 KB) for PM-0001-23's 128 kbps limit. For PM-0001-24's bottleneck it holds the larger of 200 ms at the bottleneck rate and 4 datagrams. Both values go in the run header". HIGH.
- F5.2 So ImpairSocket models a shaper, not a policer: per peer and direction, a FIFO serialising at rate R (departure = max(t, link_free_at) + bytes x 8 / R) with a drop-tail limit Q in bytes, before the profile's delay, jitter, loss and reorder step; tail drops counted apart from profile losses; throttle start and end stamped. Count bytes as the UDP payload + 28 B per datagram, the convention of the ADR's per-client cap (ADR 0001:290, :1544). HIGH (follows from the rows); the order (queue first, then delay) is my proposal.
- F5.3 It must never push back on quinn (no WouldBlock, poll_writable always Ready): a network drops, and quinn's connection driver treats WouldBlock as host backpressure, holding the transmit and stalling that connection (quinn connection.rs:1048-1069). The bottleneck has to reach the server through loss and queueing delay in quinn's RTT, or -24 cannot see what it tests. HIGH.
- F5.4 Arithmetic for Q: "about 4.1 KB" = 4 x (about 1,028 B payload + 28 B) = 4,224 B, the snapshot datagram size (1,000 B cap + overhead). But quinn's MTU discovery lets packets grow to 1,452 B (quinn-proto config/transport.rs:750), so 4 truly full datagrams are 4 x 1,480 = 5,920 B. At 128 kbps (16,000 B/s): 4,224 B = 264 ms of queue, 5,920 B = 370 ms. For -24: R = 0.5 x S, S <= 256 kbps (the per-client cap) so R <= 128 kbps and 200 ms x R / 8 <= 3,200 B < 4,224 B: the 4-datagram floor always wins under the cap (the 200 ms term binds only above R = 169 kbps with 4,224 B, 237 kbps with 5,920 B). HIGH (arithmetic).
- F5.5 Consequence to flag: -24's mark is "the newest snapshot the client holds never older than 3 snapshot intervals (100 ms at 30 Hz)", from the server's send stamp; at P2, 50 ms of that is one-way delay, leaving about 50 ms of queueing, while a full 4-datagram queue at R = 64 kbps (S = 128 kbps) drains in 528 ms. Loss-based NewReno/Cubic fill a drop-tail queue before they back off, so -24 passes only if the server's own rate adaptation keeps the bottleneck queue near empty (RTT-driven). That is what -24 tests, but the queue floor makes it hard by construction; the advisor should confirm the floor is meant. MEDIUM (depends on real snapshot sizes and how age is computed).
- F5.6 Related, outside ImpairSocket: quinn's datagram send buffer defaults to 1 MiB (quinn-proto config/transport.rs:396) and `send_datagram` drops the oldest only when that is full (quinn connection.rs:448-454; quinn-proto connection/datagrams.rs:155-156): at 8,000 B/s that is about 2 minutes of stale snapshots, the -24 bite "a blocking send that queues every snapshot" in another form. npt-net should set `datagram_send_buffer_size` to a few datagrams or gate on `datagram_send_buffer_space` (ADR 0001:442 asks for the latter). HIGH (defaults); the size to pick is a design choice.
- F5.7 B1, the UDP block and per-peer profiles live in the same per-peer flow state: B1 = drop every datagram both ways in a stamped 1 s window on top of P2; the UDP block (-29) = drop both ways until lifted, counted. The table is keyed by the peer's address (normalise IPv4-mapped IPv6 if the socket is dual-stack), bounded (security F13), with a default profile for unknown peers; iteration in a BTreeMap or by sorted key (the workspace denies iter_over_hash_type: Cargo.toml lints). HIGH for the mechanics; QUIC migration moves a peer to a new address and loses its profile (wtransport's builder enables migration by default: config.rs:544 `migration: true`): see open questions.

### Q6 (PM-0001-3's L2 probe): done
- F6.1 Yes, raw UDP through ImpairSocket without quinn, driving the very type through its AsyncUdpSocket methods (try_send, poll_recv) so the code under test is the code quinn calls. Under quinn the probe would measure quinn: its congestion control caps 10 kpps under 2-5 % loss, its ACK packets mix into both directions, and encryption hides the probe's sequence numbers from the impairment layer. Probe run 1 shows the raw path works: 10,000 of 10,000 released and received at ~10 kpps. HIGH (reasoning plus the run).
- F6.2 Shape: RS's probe port sends 10,000 pps down; LG's probe sender (unimpaired) sends 10,000 pps up; a flagged subset of downstream packets is echoed by LG inside its upstream packets, so the round trip is measured on RS's clock alone (release of the echo minus the original try_send). One-way delays are stamped at the impairment layer on RS: outbound = release - try_send, inbound = release to the reader - the reader's arrival stamp. The path's own one-way share cannot be split without clock sync; the base RTT (median of 10 s of pings, PM-0001-3) is the P0 echo. HIGH.
- F6.3 Log, per datagram: direction, seq, arrival or hand-over stamp (ns, RS monotonic), fate (delivered, profile loss, burst loss, blocked, tail drop, swapped), the drawn delay, due time, actual release, lateness = release - due. Per run header: profile values, measured base RTT and method, the injected one-way delay per direction ((profile RTT - base RTT) / 2: R-9), jitter half-width, loss, reorder rate, B1 window, seeds per direction (never clock-derived), the ImpairSocket build hash, clock source, clock-thread mode and timer slack, kernel version, rates and payload size. Aggregates per direction: loss, mean delay, the delay histogram against uniform (the ADR's bite: a normal jitter fails), reorder share, lateness p50/p99/p99.9/max (the advisor's 0.25 ms condition), RTT mean/median/p99 from echoes, and kernel UDP counters before and after on RS and LG (/proc/net/snmp InErrors, RcvbufErrors, SndbufErrors) so host drops are not counted as injected loss. HIGH as a list; the counters' path is standard Linux, not checked on RS.
- F6.4 The jitter model decides whether the probe can pass. With an independent delay per datagram (netem's tfifo: "Packets will also get reordered if jitter is large enough", iproute2 tc-netem.8), the delivered one-way delays are exactly the drawn uniform, so PM-0001-3's bands can pass, but packets 0.1 ms apart reorder about half the time, and so do QUIC packets sent back to back in the game, which feeds quinn's packet-threshold loss detection (3: quinn-proto config/transport.rs:382). ADR 0001 part 13 assumes this model ("One run at P4, whose jitter reorders on its own", docs/adr/0001-multiplayer-netcode.md:580-585). With FIFO per flow (netem's pfifo, the plan's WebSocket model), order holds, but at 10 kpps each datagram waits for the one before, the delays are no longer uniform, and the probe fails its bands unless it spreads its 10,000 pps over many flows each slower than the jitter range (for example 500 ports x 20 pps). Recommendation: independent per datagram as the ADR assumes, with quinn's lost-packet count minus ImpairSocket's injected drops logged per run as the spurious-loss measure; FIFO stays a recorded switch. Advisor to confirm. MEDIUM.
