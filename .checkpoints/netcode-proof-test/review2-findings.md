## netcode-architect: REVISE. Four findings are High (F1 to F4) and none is Critical. All four are text changes to the plan, and none needs a new design round. F1: the link and client-endpoint interfaces have no path for stream messages. F2: the WebSocket delay wrapper has no loss or stall model. F3: R-17's one-interval queue is smaller than one datagram. F4: nothing says which command-timing option (OQ-0001-6) the rule cap and Mustafa's checklist use. Once these are fixed, each Medium goes in before the step it affects: F2 and F3 before U3; F1, F9, F10 and F12 before U4 and U6; F4 to F8 in the run plans for R2, R3 and R7. OQ-0006-16: I agree with section 8.1's port numbers, on three small conditions (picks, R-1).
- **NC2-F1 High** (4.7 (npt-link), E7 (npt-client)): The interfaces cannot carry stream messages. poll_recv returns (bytes, arrival) with no channel. ClientEndpoint::input takes only datagrams, and StepOut returns only datagrams. So Join, JoinAccepted, FullState, Resync, ClientSettings, RoomEnded and SessionControl have no route, and the receiver cannot tell a control-stream message from a datagram. Three more things are missing: a send result (the non-waiting send_datagram with its buffer-space check), the maximum datagram size, and the count of unsent snapshots that the WebSocket newest-only rule and -31 need. The plan calls 4.7 each crate's whole public surface, and the boundary spike keeps E7's shape. **Change:** Link: poll_recv(now) -> Option<Recv{channel: Datagram|Control|FullState, bytes, arrival}>; send_unreliable returns SendResult{Sent, BufferFull, TooLarge}, which is counted and feeds rate adaptation and -24's bite; add max_datagram_size() and unsent_unreliable(), with the WebSocket newest-only replace inside the backend; Listener also yields the peer address. Endpoint: input(page_input, received: &[(Channel, bytes, arrival_ms)], prev_send_ms, now_ms) and StepOut{datagrams, reliable: [(Channel, bytes)], block, next_due_ms}, still one input call and one step call per tick. A message on the wrong channel is dropped and counted as forged (-21).
- **NC2-F2 High** (E15, U3, R-25 (DelayStream)): The in-process WebSocket wrapper is described only as a delay. Nothing says how P2's 2 % loss per direction shows on TCP: as a head-of-line stall. Nothing keeps delivery in order under jitter. Nothing bounds the wrapper's buffer, so the server never feels backpressure. As written, -31 (WebSocket stalls) cannot fail on loss, the server's newest-only drop never fires, and checklist step 13 does not really run at P2. **Change:** Write the model into E15. Per direction: cut the bytes into segments of at most 1,448 B; give each segment the profile's one-way delay plus jitter; deliver each at max(the previous segment's delivery, its own time), so order holds. Each segment is lost at the profile's rate, drawn on its own, and is then delivered one retransmission timeout later (proposed: max(200 ms, 2 x the profile's round trip); Linux's 200 ms minimum is from memory and still to verify), holding back every later byte. The write side is bounded (proposed 64 KB, ADR 0001:442) and returns Pending beyond that. Count stalls per run; -31 counts only if the stall share is above 0. U3 checks the stall count at P2 on loopback. This goes to R-PR as a setup value.
- **NC2-F3 High** (R-17 (the rate limiter)): The drop-tail queue holds 'one snapshot interval'. At -23's 128 kbps that is 128,000 / 8 / 30 = 533 B. At -24's 50 % of about 146.1 kbps it is about 304 B. Both are smaller than one 1,000 B datagram plus 28 B, so the queue drops every full-size datagram whatever the server does, and -23 can fail because of the simulator. With so shallow a queue, -24's age bound can never fail through queueing, so the controller choice (NewReno or Cubic, R2-BUD-OQ10) is made without testing the delay feedback the draft relies on. **Change:** For -23, a queue of at least 4 full datagrams (about 4.1 KB). For -24, a depth in time above the mark's bound (proposed: 200 ms at the bottleneck rate, and at least 4 datagrams), so a server that ignores the bottleneck fails on age, as the draft's own bite intends. Record both values in the run header and send them to R-PR.
- **NC2-F4 High** (6.2, 7.2 (R3, R7), 11 item 3; order constraints): Only -20 runs under both command-timing options (OQ-0001-6). Yet -56's record needs -42's correction share, -48's registration and -49's honest rewind at P2 to P4 for each option, and R3's 1.0 h for -48 and -49 fits one option. The buffer adds 33.3 to 100 ms to every rewind, so the rule cap depends on the option, but the plan never says which option sets the cap, runs -49's rule-cap run, or is in play during Mustafa's checklist. It also leaves the cap to be worked out in the middle of an unattended R3. **Change:** Run -42 (L1, plus R7 on the laptop stand-in), -48 and -49 (L1 and R3) under both options at P2 to P4. Add an order rule to 7.2: R3's test-cap runs under both options; this container judges them and picks OQ-0001-6 by its rule (-20, -21, -41, -42 and -60 on L1, and -48), and the advisor confirms the pick; the rule cap is then that option's honest-rewind p99 at P2, rounded up to whole ticks; -49's rule-cap run moves to the start of R7; the checklist runs under that option and cap. R3's hours stay about the same, and R7 gains about 0.7 h, inside its cap.
- **NC2-F5 Medium** (E12, npt-lab, R7): The rule cap comes from L1 and LG bots that send 30 inputs per second with no frame loop. The draft lists the wait from the drawn frame to the tick as one part of the honest rewind (0 to one frame), so the bots' rewind runs low by up to a frame. Brave on a home connection can then go over the cap, and steps 7 and 10 would clip honest shots. **Change:** The target-course shooter on L1 and LG runs a page-like 60 Hz frame loop with a seeded phase, posting its input and view time each frame. In R7, before the checklist, compare the laptop stand-in's Chrome honest-rewind p99 at P2 with the rule cap. If Chrome's p99 is above the cap, stop and take it to the advisor.
- **NC2-F6 Medium** (7.2 R3 and R4 (H17: clean references before -24 and -25)): The draft defines a clean reference as the median of 3 clean runs whose p99s lie within 2.5 % of their median. R3 has no clean runs for -24, and R4 has only one for -25. Never take a reference from another run's VM. This adds about 0.6 h to R3 and 0.4 h to R4 (R4 then plans 4.9 h of its 5).

R2 (S30s at P2 on L2) and R7 (the laptop stand-in's legs over L2) list no probe in their hours. - **NC2-F9 Medium** (4.7 (npt-lab L1Scenario step order)): The step order 'packets, server tick, clients' leaves several things undefined. Client frames are missing, though the L1 legs of -42, -45, -61 and -62 are judged per frame. Clients have no clocks of their own (offset and rate), which -47's random offsets and -21's 1.5x clock need. Ping answers on the I/O runtime have no step. A zero-delay packet at P0 has no delivery rule. The tick schedule's arithmetic is not given, and 10^9/30 ns is not a whole number. L1's RTT reads the simulator's true value, which makes -50's L1 legs optimistic. **Change:** Define each instant as: (1) packets due, ordered by arrival time and then fate-log index, never delivered in the instant they were sent (P0 included); (2) the server's I/O step: decode, socket checks, ping answers; (3) the server tick if due, with tick k due at base + floor(k x 10^9 / TICK_HZ) ns; (4) the client frames that are due (60 Hz, seeded phase); (5) each client whose next_due_ms has come, in slot order. Give each client a host clock of offset + rate x SimClock (seeded; rate 1.5 for -21's cheat). Make L1's RTT an RFC 9002-style smoothed estimate. Draw packet fates per (seed, link, direction, packet index), so both command-timing options see the same losses.
