## Block 2. MUL-ADD's check on the built file (DONE)
**What 3a found** (report :121-140; crates/devtools/vectors/f32-expected.txt:41-58; my probe B2-6). The 16 pinned cases are 10024-10039 of the 48 constructed ones: a = +-0x01000001 (2^-125 x (1 + 2^-23)), b = 0x32FFFFFE (2^-25 x (1 - 2^-23)), so a x b = +-2^-150 x (1 - 2^-46): just under half the spacing of f32 subnormals (2^-149); c = +-0x007FFFFF, +-0x00400001, +-0x00012345, +-0x00000041 (subnormals, all odd). The exact a x b + c is c itself (the product is less than half a unit away). The software routine computes c + a x b in f64, where the 2^-196 part is lost, leaving c +- 2^-150 exactly: a tie between two f32 subnormals, which the narrowing breaks to even, moving c by one unit (up when product and c share a sign: 007FFFFF -> 00800000; down otherwise: 007FFFFF -> 007FFFFE). Its tie correction (libm's generic::fma_wide_round, src/math/generic/fma_wide.rs:23-36, the same family as the toolchain's) looks for the tie at a fixed 29 bits below the f64 significand's top, the right place only when the f32 result is normal (24 significant bits). Natively the FMA instruction is exact. Reproduced here in Node with the pinned toolchain (B2-6). Plain a x b + c gives 007FFFFF on the first case: two roundings are right there, the "fused" routine is not.

**What in a .wasm file can be a fused multiply-add:**
1. A call to the toolchain's own routines `fmaf` / `fma` (compiler_builtins, v0-mangled internals `...libm_math3fma3fma`): every std `f32::mul_add` / `f64::mul_add` (B2-6), num-traits' Float::mul_add with std (float.rs:1957), simba's mul_add without libm_force (complex.rs:286-287).
2. The libm crate's own `fmaf` / `fma` (pure Rust, legacy-mangled `_ZN4libm4math4fmaf4fmaf17h...E`): simba's mul_add with libm_force (complex.rs:582-583, 856-857), glam's VecN::mul_add with its libm feature (math.rs:139-140), num-traits without std (float.rs:2098, 2144), and libm's own cbrt (cbrt.rs:106-137). Natively on x86 this one dispatches at run time to the FMA instruction (B2-1), so it is no more portable than std's.
3. A relaxed SIMD instruction: f32x4.relaxed_madd/nmadd, f64x2.relaxed_madd/nmadd (0xFD 261-264, B2-8). Nothing else in WebAssembly 3.0 fuses; scalar f32/f64 ops never do, and an engine may not contract them.
4. A routine the host provides through an import (none exists in JavaScript today; a name check is cheap).
5. A hand-written fused routine under another name inside a dependency: only a source audit sees it (done for parry3d, glamx, glam, simba, wide, num-traits, libm at their versions: B2-2, B2-9 below).

**How to find each in the production file** (`packages/sim-worker/pkg/sim_wasm_bg.wasm`):
- Names: the production file still keeps its name section today (3b: 10,220 of 53,783 B; wasm-bindgen keeps it by default), but 3A-NAME-SECTION plans to drop it. - Opcodes (3): walk the production file's code section itself, instruction by instruction (names not needed). Rule: no 0xFD-prefixed instruction at all while SIMD is off (PM-0004-25), the four fused ones named in the message; an opcode the walker does not know fails the check (fail closed). Second, cheap signal: the twin's `target_features` section (present, B2-6) must not list `+simd128` or `+relaxed-simd`.
- Imports (4): `WebAssembly.Module.imports` on the production file: every import from wasm-bindgen's module with a `__wbg_` or `__wbindgen_` name, none naming fma or a maths function. The same list gives PM-0004-10's Wasm half (no host time import: refuse `__wbg_now_*` and the like) at no extra cost.
- Demangling: two schemes are present (B2-6): legacy `_ZN...E` (our crates, registry crates) and v0 `_R...` (compiler_builtins). Both carry their path as length-prefixed identifiers, so one scan of `<digits><identifier>` tokens gives the path for either; no full demangler is needed.
