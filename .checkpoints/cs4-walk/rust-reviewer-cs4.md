8. Vertical move: sweep by dy; a hit while falling on a walkable normal lands (y at TOI, vy = 0, grounded); a hit while rising stops vy.
9. Ground snap: grounded last tick and not jumping, but no ground within dy: sweep down by stepUp; walkable hit -> snap and stay grounded (ramps and stairs going down); else airborne (walked off a ledge).
10. Walkable = normal.y >= MAX_WALK_NORMAL_Y, a cosine stored as data (Quake III's 0.7, R4-PHYS-F24), so no trigonometry.
11. Facing: normalise (aim.xz - pos.xz) with sqrt; keep the last facing when the length is 0.
After all soldiers moved: the soft push (START-RULES: "they push each other softly and never block"). Soldiers never collide in the sweeps. For each pair (i < j) in slot order: horizontal circle overlap plus vertical span overlap with our own maths (d = sqrt(dx^2 + dz^2); overlap = ri + rj - d). Not parry's capsule-capsule contact: it runs a fresh EPA exactly when the capsules overlap (B3-1), which is every tick two soldiers touch, so it would allocate in the step; push each by PUSH_SOFTNESS x overlap / 2 along the horizontal normal; equal centres take a fixed direction by slot order (no randomness). Pushes are summed per soldier from the post-move positions and then applied through a horizontal sweep against the statics (order-free, and never into a wall). PUSH_SOFTNESS is game-designer's (proposed 0.25 per tick). Mark -35's "soldier pairs" is then the soldier's capsule against every static shape kind; see the marks block.
Debug and test builds assert every position and velocity finite after the tick (PM-0004-24).

**Float operations: on part 7's list or not.** Ours: + - x / and negation, comparisons and total_cmp, sqrt, abs, copysign, our three helpers, `as` casts, is_finite, to_bits/from_bits: all on the list. Not on it: `exp` for K (step 4: pinned libm at load, or data). mul_add: never (MUL-ADD). No trigonometry anywhere in the step. Constants (G_DT, HALF_G_DT2, K, speeds) are computed once at load and are part of the content hash's inputs, never recomputed per tick.
parry's own operations on these paths: GJK, support maps, the binned build, ray-box slabs: + - x /, comparisons, sqrt (glam's length -> libm sqrtf: a soft square root on wasm32, exact; sqrtss natively, exact), fabsf, copysign (wops.rs:32), std's min/max/clamp in core (185 places; same bits on both targets today, B2-7), saturating float-to-usize casts. Outside the list and target-dependent: only what we do not call (std transcendentals with std on, B2-5; libm's fmaf, B2-1; wide's backends, B2-3). With parry's std off they would go to libm anyway (B1-12).

**Is `enhanced-determinism` enough for PM-0004-20?** For these paths, by reading: yes together with three choices it does not make by itself: parry's std off (or its std-only paths avoided), typed calls (no `dyn Shape` vtables that would link sin_cos), and no mul_add (the built-file check). PM-0004-20's times (flag on against off) are Slice 6's by Part 3.4 (line 626); with the flag off, indexmap leaves the tree and parry's maps become hashbrown + foldhash FixedState, so a flag-off build is a separate configuration to compare, never the game's.

## Block 4. The integer time unit (DONE)
**What the drafts ask.** ADR 0004 part 4 (:191-201): durations authored in seconds, converted at load to whole sub-tick units "in which one tick is an exact whole number", rounding reported, timers carry their remainder; the units-per-tick figure set from the rounding report. PM-0004-11 (:1132): the loader's report lists every duration of the legacy tuning with its rounding, the figure is written beside it, 0 legacy intervals under one tick at 30 Hz, bite: a planted 0.02 s interval flagged for game-designer. PM-0004-9 (cs8) and PM-0004-72 (60 Hz reading at cs8): every legacy interval's shot count within 1 shot of 60/interval, the same at 30 and 60 Hz.

**The report** (a script with a `--check` mode like the vector generators, e.g. `crates/devtools/vectors/make_time_report.py` or a devtools binary; it reads, never writes the tuning):
- Input: docs/legacy-tuning.json and a committed, reviewed list of duration paths with their unit (seconds or milliseconds), e.g. `WEAPONS.*.fireInterval s`, `WEAPONS.*.burstInterval s`, `WEAPONS.*.reload s`, `T.meleeCooldown s`, `TUNE.ai.retargetS s`, `WR_DEPLOY_MS ms`; every numeric leaf NOT on the list is listed once under "not a duration" so a missed one is visible (B4-1). game-designer confirms the list (it is a rules reading), as for Testlines' table.
- Per duration and per candidate U (60, 600, 3000, 6000, 60000 per second): the exact value of the JSON double (Fraction), n = round(d x U), the error n/U - d (absolute, relative), the value in ticks at 30 and 60 Hz, and for fire and burst intervals the shot count over 60 s with a carried remainder against 60/d; a flag for anything under one tick at 30 Hz.
- Output: one table (Markdown) committed, plus its sha256; `--check` fails when the tuning, the list or the result changed.
- The same conversion function the content loader uses (Rust) produces the numbers that are committed; the script's Fraction arithmetic is the independent reference (as the f32 vectors' Python is for 3a).

**Recommendation: U = 3000 units per second** (one unit = 1/3 ms). It is the least common multiple of 1000 (every legacy duration is a whole millisecond: B4-1) and 60 (a 30 Hz tick = 100 units, a 60 Hz tick = 50 units: both whole), so every legacy duration converts exactly and a duration in units does not depend on the tick rate (only UNITS_PER_TICK changes, 100 -> 50, so PM-0004-72's "durations re-converted" is a no-op). u32 holds 1,431,655 s (16.6 days) of units, i32 half that: far past a match. 6000 and 60000 are as exact with less range and no gain; 1000 (milliseconds) fails part 4's "one tick is an exact whole number" (33.33 units per 30 Hz tick); 600 fails PM-0004-9 on the Shabzon (B4-1). If R1-TICK-OQ1 ever picked 64 Hz, U would become a multiple of LCM(1000, 64) and the report would be rerun: noted, not planned (TICK-30).

**The conversion** (content crate, at load, never per tick): `units_from_seconds(d: f64) -> Result<u32, DurationError>`: refuse non-finite, negative, and anything whose units exceed u32; n = `(d * 3000.0).round()` in f64 (multiply and round are on part 7's list and exact IEEE operations; f64 because the JSON double is f64); report entries carry n and the error. 0.072 -> 216, 0.06 -> 180 (1.8 ticks at 30 Hz), 0.02 -> 60 units < 100: flagged (the bite). Constants in `sim`: `UNITS_PER_SECOND: u32 = 3000`, `UNITS_PER_TICK: u32 = UNITS_PER_SECOND / TICK_HZ` with a const assertion that it divides exactly (and that 60 Hz would too).

**What Walk itself needs:** the report and the unit chosen and committed (PM-0004-11 is placed at 4, "read again in 8"), the two constants and the conversion with its tests; no timer runs in Walk unless game-designer brings sprint stamina into it (legacy STAM: max 7, regen 0.2, lockUntil 0.3 as a fraction of the bar, GP3), in which case stamina is counted in units too. Movement's own constants (speeds, accel's K, gravity, jumpV, stepUp) are not durations. ADS's 0.55 is a factor (SLICE-FEEL); the sprint-to-fire delay is change-set 8's first timer.
